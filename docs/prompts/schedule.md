## 2026-11-05 — импорт расписания из РУЗ в БД

- **Кто ставил:** Legpopov.
- **Промпт:** «Да, пиши импорт» — продолжение предыдущей записи.
- **Интервью (скилл grillme), 4 вопроса:** куда класть данные → сразу PostgreSQL с каркасом;
  какие группы → весь вуз; период и скорость → весь семестр, по одному запросу с паузой 1 с;
  фиксировать ли изменения → да, журнал изменений.
- **Что сделал ИИ (Claude Code):** нашёл `/api/dictionary/groups` (все 1534 группы одним
  запросом) и `/api/dictionary/lecturers`; замерил объём (семестр одной группы ~3 МБ, ~3 с);
  посмотрел диффер в Ikanam-schedule и перенёс его правила на РУЗ, где у занятия есть
  стабильный `lessonOid`. Написал каркас `app/` (настройки, БД, модели), миграцию Alembic,
  клиент РУЗ, белый список полей, генератор вымышленных ФИО, импортёр с журналом изменений,
  CLI, 22 теста на поддельном сервере РУЗ.
- **С первого раза:** клиент, нормализация, миграция (autogenerate), CLI.
- **Пришлось переделать:**
  - вставка занятия падала на NOT NULL `last_seen_at` — поймали тесты;
  - при сбое группы посередине не откатывались кэш преподавателей и счётчики в памяти —
    заметил ИИ на самопроверке до запуска тестов;
  - аудит БД после живого импорта нашёл вымышленную фамилию, совпавшую с фамилией реального
    преподавателя → добавлен стоп-лист фамилий из справочника РУЗ.
- **Проверка:** живой импорт 5 групп за семестр (3233 занятия), два повторных — без ложных
  изменений; аудит БД по всем 3424 преподавателям — ни ФИО, ни email.
- **Не сделано:** полный прогон по всему вузу, проверка на PostgreSQL.
- **Итог:** раздел «Реализация» в [0002](../decisions/0002-schedule-source.md).
