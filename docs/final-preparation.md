# Подготовка к финалу МГИМО: выводы из хакатона МФТИ

Дата: 15 ноября 2026. Источник — предварительная рефлексия Legpopov и уточнения в диалоге.
Это дополнения команды к плану MGIMO-LMS, а не новые официальные требования организаторов.
Статус пунктов ниже — запланировано; реализация и прохождение проверок этой записью не подтверждаются.

- [ ] Разделить постоянные и переменные расходы: API генерации, эмбеддинги, обновление корпуса, сервер, хранение и сопровождение.
- [ ] Записать допущения о нагрузке, токенах, повторных вызовах и кэше; у тарифов указать источник и дату проверки.

- [ ] Подготовить воспроизводимый расчёт и итоговый слайд для защиты.

## 2. RAG совместно с API генерации

Связанные задачи: [#12](https://github.com/Ekanam-Friends/MGIMO-LMS/issues/12),
[#26](https://github.com/Ekanam-Friends/MGIMO-LMS/issues/26).
Ответственный за доработку не назначен этой записью.

- [ ] Использовать наш поиск по открытым положениям МГИМО вместе с генерацией через API; предпочтение — YandexGPT или GigaChat, как в [решении 0007](decisions/0007-rag-assistant-infra.md).
- [ ] Передавать модели найденные релевантные фрагменты и метаданные; требовать ссылки на документ, пункт/страницу и редакцию.
- [ ] При недостаточных основаниях уточнять запрос или сообщать, что подтверждённого ответа нет.
- [ ] Сравнить кандидатов на одном наборе вопросов по качеству, времени ответа и стоимости; выбрать провайдера по результатам.

По оценке Legpopov, Qwen3 4B в опыте МФТИ не подошла для генерации. Это вывод о том
использовании, а не доказательство непригодности модели для любых задач. Ошибка
«оформление отпуска» → положение о командировках могла возникнуть на этапе поиска,
выбора контекста или генерации: точная причина здесь не установлена. Более сильная
API-модель сама по себе не заменяет проверку поиска и источников.

Вызовы — только с бэкенда, ключи — только в окружении сервера. В контекст этой функции
передаются открытые положения; реальные персональные данные в корпус не включаются.

## 3. Соответствие ответов положениям

- [ ] Подготовить контрольный набор: вопрос, эталонный документ и пункт/страница, ожидаемые факты, дата актуальности, допустимое уточнение или отказ.
- [ ] Раздельно проверять поиск нужного положения, подтверждение каждого существенного утверждения источником и корректность редакции.
- [ ] Включить регрессию МФТИ: «оформление отпуска». Если вид отпуска неоднозначен — уточнить его; совпадение слов в положении о командировках не считается основанием для ответа об отпуске.
- [ ] Добавить близкие темы, разные формулировки, вопросы вне корпуса, противоречащие фрагменты и запросы на разные даты.
- [ ] Сохранить отчёт: снимок корпуса и дату его проверки, провайдера/модель, настройки, найденные фрагменты, ответы, ссылки и результаты ручной сверки.

Критерий готовности: все согласованные обязательные кейсы проходят ручную сверку;
существенные утверждения подтверждены нужными пунктами, ссылки ведут к ним, нет
подмены темы или редакции. Ошибки исправлены и проверены повторно, ограничения
описаны. Самооценка модели не заменяет эту проверку.

## 4. Финальная презентация в стиле МГИМО

- [ ] Подготовить цельную презентацию: академичный стиль, сине-белая палитра, аккуратная типографика, читаемые схемы и скриншоты. Официальный логотип вуза не использовать.
- [ ] Выстроить рассказ: проблема очередей в деканат → сценарий студента → демонстрация кабинета → RAG и источники → результаты проверок → юнит-экономика → ограничения и развитие.
- [ ] Показать только проверенные возможности и результаты; отделить планы от реализации. Сохранить обозначение конкурсного концепта.
- [ ] Подготовить редактируемый файл и PDF, проверить отображение, порядок слайдов и провести репетицию с замером времени. Длительность выступления уточнить по регламенту.

Это отдельный материал команды; презентация не подменяет обязательный документ
о процессе [#17](https://github.com/Ekanam-Friends/MGIMO-LMS/issues/17).
Ответственный за презентацию пока не назначен.

## 5. Актуальность документа на выбранную дату

На МФТИ, по сообщению Legpopov, выбор даты приводил к отсутствию ответа: система
искала документ ровно этой даты. Для МГИМО требование — определить редакцию,
**действующую на выбранную дату**, а не искать совпадение даты документа.

- [ ] Учитывать дату вступления в силу, изменения, замену и отмену. Дата публикации или скачивания не равна дате начала действия.
- [ ] Для выбранной даты брать последнюю вступившую в силу редакцию, не заменённую и не отменённую к этому дню. Более поздняя редакция не должна менять исторический ответ.
- [ ] Проверять наличие новых редакций в официальном источнике; показывать дату последней проверки корпуса. Без неё нельзя утверждать, что более нового документа нет.
- [ ] Если исторических редакций или метаданных не хватает — явно сообщать ограничение, не выдавать текущий документ за исторический.
- [ ] Проверить даты между редакциями, точно на границе вступления в силу, после последней редакции, до первой известной, после отмены без замены и при неполных метаданных.

Критерий готовности: дата между редакциями даёт ответ по действовавшей тогда редакции,
а не пустую выдачу из-за отсутствия файла с такой же датой. В ответе видны основания
выбора и ограничение свежести. Подробнее — [решение 0011](decisions/0011-rag-answer-quality.md).

## 6. Несколько агентов для микрозадач

Идея Legpopov: несколько агентов выполняют отдельные микрозадачи, затем их результаты
обрабатываются в полноценный ответ. Это вариант для оценки, окончательная схема не выбрана.

- [ ] Проверить разделение ролей: уточнение намерения → поиск → выбор редакции → составление ответа → проверка утверждений и ссылок.
- [ ] Передавать между этапами источники и метаданные, а не только свободный пересказ. Сборщик ответа не должен добавлять неподтверждённые факты.
- [ ] Сравнить с простым RAG на том же контрольном наборе: качество, задержка, число API-вызовов и стоимость; результаты включить в юнит-экономику.
- [ ] Определить поведение при конфликте результатов и сбое агента: уточнение/отказ вместо неподтверждённого ответа.

До внутреннего срока нужно принять и записать решение, нужна ли эта сложность.
Внедрение схемы зависит от результатов сравнения; её нельзя считать готовой по одному
описанию ролей.

## 7. Проверка действий в отношении студента

Предложение Legpopov от 15 ноября: проверять обоснованность и законность действий
в отношении студента на основании локальных нормативных актов вуза и актов
Минобрнауки. Сценарий добавлен в [roadmap](../ROADMAP.md), реализация предстоит;
ответственный пока не назначен.

- [ ] Подготовить проверенный корпус открытых локальных актов и релевантных актов Минобрнауки из официальных источников; фиксировать реквизиты, редакции, сроки действия и дату проверки источника.
- [ ] Принимать описание действия, дату события и необходимые обстоятельства. Примеры для вымышленных кейсов: отчисление, дисциплинарное взыскание, отказ в академическом отпуске или стипендии.
- [ ] Сопоставлять основания и порядок действия с применимыми нормами: условия, сроки, уведомления, необходимые документы. Проверять применимость и соотношение актов; возможные противоречия показывать явно, со ссылками.
- [ ] Формировать разбор: известные обстоятельства → нормы с точными ссылками → сопоставление → подтверждённые основания и признаки возможного нарушения → недостающие сведения и вопросы для проверки.
- [ ] При отсутствии документов, неполных фактах или спорном толковании обозначать неопределённость; не делать категоричный вывод о законности только из-за отсутствия запрета в найденных фрагментах.
- [ ] Проверить набор вымышленных кейсов: действие соответствует нормам, нарушен порядок, нет основания, конфликт актов, устаревшая редакция, недостаточно сведений. Эталоны и выводы сверить с профильным экспертом.

Критерий готовности: выводы в контрольных кейсах подтверждены применимыми нормами
на дату события, факты отделены от предположений, пропуски и противоречия обозначены.
Сценарий помогает проверить основания решения; автоматическое принятие решений
по студентам в этот пункт не входит. Для демо используются только вымышленные
обстоятельства и данные студентов.
