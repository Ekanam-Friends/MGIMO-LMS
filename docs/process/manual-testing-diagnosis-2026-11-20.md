## Неполный нормативный ответ и OCR

В неизменившемся корпусе фрагмент `000427-53` содержит начало пункта 43 и только
подпункт «а» (472 символа). Следующий фрагмент `000427-54` начинается с `6)`
и включает продолжение критериев, в том числе «в)». Это согласуется с ошибкой OCR:
буква «б» распознана цифрой 6. Функция `fragments` в
`scripts/rag/publish_snapshot.py` считает начало строки с цифрой и скобкой новым
пунктом, поэтому логический список разорван. Сверка соответствующего места
с изображением оригинальной страницы в этой диагностике не выполнена.

При этом `evidence_context` уже добавляет соседние фрагменты: считать полное
отсутствие соседнего текста единственной причиной неполного ответа нельзя.
Исторические draft/audit не сохранены, поэтому причины отбрасывания каждого
из пяти элементов на скриншоте неизвестны.

Исправление: сверить проблемные страницы, восстановить структуру пункта 43 и
его подпунктов, сохранить связь частей списка и диапазон страниц, после чего
пересобрать индекс. Не заменять все `6)` на `б)` автоматически: в документах
могут быть настоящие шестые пункты. Проверить отдельно полноту условий и исключений,
включая соседний пункт 44. Снимать отметку `snapshot` можно только после проверки
OCR и метаданных применимости: сам по себе частичный статус здесь корректен.

Словарь `corpus.expand` уже знает «стипуха» → «стипендия». Поэтому предложение
«просто добавить этот синоним» не устранит обнаруженные причины.

## Ошибка GigaChat: что удалось воспроизвести

Ограниченный прогон 20 ноября на текущей конфигурации дал:

| Проверка | Результат |
| --- | --- |
| ROUTE: общий вопрос об условиях повышенной стипендии, без истории | `public`, корректная поисковая формулировка; лишний запрос оценок в этом прогоне не повторился |
| ROUTE: «А что по стипухе?», без истории | `public`, поиск условий назначения стипендии |
| ROUTE: «Какие условия ее получения?», без истории | `schedule, grades, requests`; поисковая тема ошибочно заменена справкой о болезни |
| Полный chat: «Что будет, если я прогуляю пару?», без истории | Маршрутизация завершилась, генерация упала с `ProviderError: Генерация не завершена или отклонена GigaChat` примерно через 3,62 с; интерфейсу вернулась общая ошибка |
| Повтор chat с тем же вопросом | Выбран личный маршрут; для диагностической беседы без выбранного студента вернулось уточнение о выборе демо-студента |
| Нормативный поиск напрямую (`ask`), с тем же вопросом | Генерация и аудит завершились с `finish_reason=stop`, получен `partial` |

Последний вызов проверяет публичную ветку отдельно от ROUTE и не равнозначен
полному браузерному сценарию. В диагностические запросы не передавались записи
студента; диагностическая беседа не сохранялась в работающем HTTP-приложении.

`GigaChat.complete` в `app/assistant/provider.py` отклоняет любой `finish_reason`,
кроме `stop`, а также пустой/некорректный content одной ошибкой. `Assistant.chat`
затем объединяет `ProviderError` и общий таймаут 70 секунд в сообщение «GigaChat
сейчас не ответил». Сеть, HTTP 429/5xx, фильтрация и незавершённая генерация для
пользователя и существующей диагностики не различаются. Автоповтор есть только
для HTTP 401; для временных ошибок и таймаутов его нет.

В первом сбойном прогоне конкретный `finish_reason` не выводился; утверждать,
что это точно фильтрация, лимит токенов или сетевой сбой, нельзя. Причина двух
исторических ошибок 19 ноября также не установлена.

Предложение:

1. Ввести безопасные коды причин: HTTP-код, timeout, finish_reason, пустой ответ,
   ошибка схемы; логировать этап, длительность и request ID без ключей и тел ответов.
2. Для временных сетевых ошибок, 429 и 5xx предусмотреть один ограниченный повтор
   в рамках общего дедлайна, учитывать Retry-After. Не повторять автоматически
   отклонение фильтром или постоянные ошибки.
3. Различать недоступность, отказ генерации и отсутствие подтверждений. При ошибке
   давать переход к положениям или соответствующему разделу, а не пустой тупик.
4. Добавить маршрутизацию общего вопроса о последствиях пропуска занятия в
   нормативную область; при отсутствии даты, дисциплины или иных необходимых
   сведений уточнять их, не подставлять личные оценки и заявления.

## Порядок исправлений и приёмка

1. Контекст диалога и различение общих правил/личных данных: цепочка о стипендии
   сохраняет тему; общий вопрос не читает оценки и не вызывает согласия.
2. Данные кабинета: задания без балла доступны по своим курсам; преподаватель
   берётся из доступного занятия; чужие данные не попадают в ответ. Задания и
   расписание не требуют согласия на оценки; без согласия оценки не читаются.
3. Расписание: выбранные подгруппы совпадают с календарём, ближайшее занятие
   определяется по московскому времени, отмены обозначены, неоднозначность уточняется.
4. Ошибки провайдера: временный сбой, незавершённая генерация и отказ фильтра
   воспроизводятся раздельными тестовыми ответами; причины диагностируются,
   автоматические повторы ограничены.
5. Корпус: сверены проблемные подпункты, критерии не теряются на границе фрагментов;
   аудит доказательств сохраняется. Затем убрать дубли цитат и повторное приветствие.

проверить экран 360 px, включая показ клавиатуры и запрос/отказ согласия. Новые
скриншоты нужны после изменения интерфейса. Этим разбором исправления не заявляются.
