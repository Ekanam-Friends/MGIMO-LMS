# Аудит большого конкурсного стенда — 17 ноября 2026

Это снимок до реализации изменений. Последующая реализация, команды и проверка
сервера описаны в [инструкции большого стенда](../contest-scale.md) и ADR 0020.

## Критерий и границы проверки

Источник задачи: Legpopov, проверка команд из переписки и архитектуры для 10К+
студентов и 1К+ сотрудников. Уточнено в интервью:

- не менее 10 000 вымышленных студентов с доступным входом;
- ориентир: 800 преподавателей с занятиями и 200 остальных сотрудников;
- одновременно работают десятки пользователей;
- расписание всех групп студентов импортировано из РУЗ; увеличение размера групп допустимо;
- результат этой задачи — аудит и команды, без изменения приложения и наполнения сервера.

Проверены файлы текущей рабочей копии ветки `feature/gigachat-evidence-assistant`,
HEAD `d849919`, включая незакоммиченные изменения. Это не проверка кода внутри
запущенного серверного образа. На сервер не подключались; число пользователей,
доступность РУЗ, сертификат и ресурсы VPS на дату аудита не измерялись.
Сведения о 24 студентах и проблеме сертификата на скриншоте — исторические сообщения.

## Вердикт по командам из переписки

| Команда или настройка | Что подтверждено текущим кодом |
| --- | --- |
| `BOT_BOOTSTRAP_GROUPS=400` | Поле добавлено локально в `app/core/config.py`, обращений к нему в приложении нет. Догрузка не реализована. |
| `BOT_IMPORT_SCOPE=students` | Аналогично: поле есть, бот продолжает выбирать только группы привязанных к Telegram студентов. |
| `docker compose up -d bot` | Применяет изменившуюся конфигурацию контейнера, но не добавляет отсутствующую логику. Для наполнения БД бот вообще не нужен. |
| `docker compose exec web python -m app.generate` | Существующая точка входа. По умолчанию 3000 студентов, по 12 на группу, только группы с занятиями и курсом до 6. |
| `docker compose exec web python -m app.generate --include-unscheduled` | Флаг отсутствует в argparse; команда завершится ошибкой разбора аргументов. Кроме того, фиктивное расписание противоречит уточнённому критерию. |
| `--reset` | Удаляет сгенерированных студентов и всю успеваемость. Для расширения наполненного стенда не подходит. |

Docker соответствует текущему способу размещения: `web`, `bot`, `db` — отдельные
сервисы в `docker-compose.yml`. `exec web` запускает процесс в существующем web-контейнере
с его кодом, зависимостями и окружением. Docker не является обязательным свойством
FastAPI или генератора, но для этого стенда это штатный способ запуска.
При изменении исходников требуется новая сборка образа; одного `up -d bot` недостаточно.
Семантика `up` сверена с [документацией Docker](https://docs.docker.com/reference/cli/docker/compose/up/).

## Что реально мешает выполнить критерий

1. **Вход массовых студентов.** `app/generate/run.py:create_students` создаёт
   `st<group_id>-<номер>` со случайными паролями, которые не сохраняются. `app.seed`
   задаёт известный пароль только избранным демо-аккаунтам. Нужен отдельный идемпотентный
   механизм выдачи доступа массовым вымышленным аккаунтам через настройку окружения.
   Пароли остаются хэшами argon2; общедоступный пароль допустим только в явно
   обозначенном синтетическом стенде. Секрет нельзя выводить в лог генерации.
2. **Расширение существующих групп.** `generate` пропускает группу, если в ней уже
   есть сгенерированный студент. Увеличение `--per-group` не доводит её до нового
   размера. Требуется режим дополнения до целевого числа с устойчивыми идентификаторами,
   созданием недостающих зачислений, баллов и итогов. Существующие ручные изменения сохраняются.
   Текущий `enroll_missing` дописывает зачисления текущего года, но не генерирует новым
   студентам всю историю успеваемости и не является полноценным расширением.
3. **800 преподавателей.** Строка в `teachers` не равна пользовательскому аккаунту.
   `app.seed:link_demo_teachers` создаёт до двух преподавательских входов. Нужен
   массовый генератор аккаунтов, связанных с уникальными `teacher_id`, у которых есть
   импортированные занятия и доступный осмысленный сценарий. Желательно также иметь
   текущую ведомость с зачисленными студентами: генератор назначает только одного
   ведущего на дисциплину, поэтому не каждый импортированный преподаватель получит курс.
4. **200 сотрудников.** Seed создаёт только `dean`. Нужны отдельные аккаунты и
   вымышленные кадровые карточки. В текущей модели у `User` одна строковая роль;
   полноценной модели подразделений и разрешений сотрудника нет. На стенде можно
   сохранить простую роль `staff`, если все 200 — демонстрационные сотрудники с
   одинаковыми правами. Если требуется разграничение по подразделениям, нужна отдельная
   модель разрешений; это продуктовое требование, не следствие числа аккаунтов.
5. **Покрытие РУЗ.** Импорт выбирает только группы с `has_schedule`. Генератор дополнительно
   отбирает группы с уже загруженными занятиями и определённым курсом до 6. Число
   пригодных групп и преподавателей нужно считать после успешного импорта. Нельзя
   обещать 800 преподавателей по одному лишь общему размеру справочника.

## Минимальные изменения архитектуры

| Приоритет | Изменение | Причина и проверка |
| --- | --- | --- |
| До наполнения | Отдельный CLI для синтетического набора: план, дополнение, аккаунты, итоговая проверка | Независимость от Telegram и доступный вход у каждого; повторный запуск ничего не дублирует и не сбрасывает. Это предложение, такой команды пока нет. |
| До наполнения | Проверка покрытия РУЗ до генерации | Выбирать группы с загруженным расписанием и обеспечить 800 преподавателям занятия; иначе явно сообщать о невыполненном критерии. |
| До нагрузочного прогона | Убрать синхронную проверку argon2 из event loop | `/login` — async, но `authenticate` вызывает синхронный `PasswordHasher.verify`. Вынос в ограниченный пул потоков, включая rehash, плюс ограничение параллельных входов. Проверить одновременный вход и отзывчивость остальных страниц. |
| До нагрузочного прогона | Ограничить процессы генерации хэшей и запускать подготовку вне показа | `ProcessPoolExecutor()` использует автоматическое число процессов; 10К хэшей могут конкурировать с web за CPU/RAM. Отдельный контейнер/процесс с лимитами, сохранение прогресса. Время заранее не обещать. |
| До приёмки | Измерить SQL и соединения на наполненной БД | Пулы существуют уже сейчас. Суммировать лимиты web, бота, импорта, генератора; подбирать по фактическим ожиданиям пула и ресурсам PostgreSQL. Индексы добавлять по планам медленных запросов. |
| До приёмки | Успешный импорт как проверяемая операция | Импортёр возвращает код 0 и для `partial`; проверять `import_runs`, ошибки и покрытие каждой используемой группы. Не считать exit code достаточным. |
| Если нужны актуальные данные всего стенда | Регулярный импорт групп всех студентов отдельной задачей с защитой от наложения | Сейчас импорт бота зависит от Telegram-привязок. Полный первичный импорт можно сделать существующим CLI. Не делать HTTP-запросы к РУЗ при открытии страницы кабинета. |
| Если масштабируется Telegram | Очередь доставки и повторные попытки, выборка получателей пакетами | Текущий tick читает все привязки, делает запросы для отдельных студентов и отправляет последовательно. В части уведомлений курсор/отметка фиксируется до успешной отправки. Для нескольких демо-привязок это не первый приоритет. |
| Если нужны несколько web-процессов | Сначала отделить фоновые задачи и общее состояние | Pyrus-sync и DocumentProcessor стартуют в lifespan каждого web; восстановление `processing` при старте не рассчитано на несколько владельцев. Разрешения бесед и ограничения ассистента локальны процессу. Миграции из старта каждого web вынести в отдельный шаг. |

Оставить FastAPI, Jinja2/HTMX, PostgreSQL, серверные сессии в БД и Docker Compose.
Число аккаунтов само по себе не обосновывает микросервисы, Kubernetes, Redis,
PgBouncer или шардинг. Один web-процесс — исходная конфигурация для измерений,
а не обещание производительности. Реплика на том же VPS не распределяет запросы
приложения и не защищает от отказа всего сервера (см. ADR 0014).

Ассистент проверять отдельно: по умолчанию допускается один активный запрос на процесс,
а остальные могут получить ответ о занятости. Это не пропускная способность обычных
страниц. При необходимости массовой работы нужны отдельный бюджет LLM, очередь,
контролируемая параллельность и измерение времени ответа. Увеличение числа
учётных записей не требует ослабления проверки ответов.

Справочные источники: [FastAPI: async и блокирующая работа](https://fastapi.tiangolo.com/async/),
[SQLAlchemy: пулы соединений](https://docs.sqlalchemy.org/en/20/core/pooling.html).

## Команды: существующие, без обещания закрыть все критерии

Ниже команды для Linux-терминала на сервере, в `/opt/mgimo-lms`.
Они здесь не выполнялись. Перед изменениями данных обязателен бэкап: `pg_dump -Fc`,
проверка `pg_restore --list`, копия вне контейнера; хранить не более трёх последних
успешных копий. Для приёмки восстановления нужен отдельный пробный restore.

Сначала проверить состояние и интерфейсы именно серверного образа:

```bash
cd /opt/mgimo-lms
docker compose ps
docker stats --no-stream
docker compose exec -T web python -m app.schedule.import_ruz --help
docker compose exec -T web python -m app.generate --help
```

После бэкапа — первичный импорт всех доступных групп за семестр:

Пример бэкапа без перенаправления бинарного архива через терминал:

```bash
mkdir -p backups
backup_file="lms-before-scale-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose exec -T db pg_dump -U lms -d lms -Fc -f "/tmp/$backup_file"
docker compose exec -T db pg_restore --list "/tmp/$backup_file"
docker compose cp "db:/tmp/$backup_file" "backups/$backup_file"
```

Продолжать только при успехе всех трёх операций. После успешной проверки результата
оставить не более трёх последних копий этого семейства и убрать временный архив
из `/tmp` контейнера. Проверка списка архива не заменяет пробное восстановление.

```bash
docker compose exec -T web python -m app.schedule.import_ruz --full
docker compose exec -T db psql -U lms -d lms -c "SELECT id, started_at, finished_at, status, groups_total, groups_ok, groups_failed, lessons_seen FROM import_runs ORDER BY id DESC LIMIT 5;"
```

Первый скрипт тянет справочники и расписание из РУЗ и заменяет ФИО преподавателей
вымышленными. Он не создаёт 10К доступных студентам аккаунтов. Если импорт частичный,
проверить список ошибок в его логе и повторить неуспешные группы через `--group`.
Проверку TLS не отключать. Историческую ошибку сертификата нужно воспроизвести
в серверном контейнере и исправлять доверие к цепочке, если она ещё существует.

Обычный seed и существующий генератор:

```bash
docker compose exec -T web python -m app.seed
docker compose exec -T web python -m app.generate --students 10000 --per-group 25
```

Вторая команда выбирает до 400 пригодных групп и создаёт по 25 студентов только
в новых группах. При 400 пустых пригодных группах это 10К новых студентов; при
меньшем числе групп или ранее созданных группах результат будет другим.
`--students` — ориентир выбора групп через округление вверх, а не строгий итоговый
COUNT и не «добавить столько». Допустимый `--per-group`: 1–40. Если даже при 40
местах пригодных групп недостаточно, существующий CLI цель не выполнит.
После запуска доступ у массовых студентов по-прежнему не выдан; 800+200 аккаунтов
не созданы. Полной существующей последовательности команд для критерия пока нет.

Для повторного обновления расписания есть окно −7…+35 дней:

```bash
docker compose exec -T web python -m app.schedule.import_ruz
```

Не запускать два импортёра одновременно. Не добавлять `--reset` для исправления
недостаточного количества студентов. Не запускать генерацию и нагрузочный прогон
одновременно: это разные проверки.

## Что измерить при приёмке

Подготовлен read-only SQL `scripts/audit_scale.sql`. Запуск из корня репозитория,
когда файл уже есть на сервере:

```bash
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U lms -d lms < scripts/audit_scale.sql
```

Если файл ещё не доставлен, его можно открыть локально и выполнить запросы
в SQL-клиенте через штатный туннель. Не предполагать наличие файла в серверном образе.

Предлагаемый профиль нагрузки, ещё не согласованный как норматив: 50 активных
сессий, затем 100; смешанные роли, переходы с паузами, расписание, успеваемость,
ведомости, сохранение баллов и объявления. Отдельно — серия одновременных входов;
отдельно — ассистент и импорт на фоне чтения страниц. Цель для обычных страниц:
p95 до 2 секунд, технических ошибок менее 1%, без потерь записей. Время LLM
и внешних API фиксировать отдельно. Эти числа — предложение для проверки,
не измеренный результат и не обещание текущего VPS.

Проверить доступ всех аккаунтов пакетно через штатную авторизацию, а не только
наличие хэша; внешние сообщения и Pyrus при нагрузочном прогоне изолировать.
Ручной сценарий на 360 px: студент видит своё расписание и оценки, преподаватель
меняет балл в своей ведомости, студент видит изменение; чужие записи возвращают
404, сотрудник работает в доступном ему сценарии. Данный аудит UI не меняет;
ручной проход и нагрузочные испытания в этой задаче не выполнялись.

Локальный запуск `--help` через `.venv` не удался: окружение ссылается на
недоступный интерпретатор Python. Синтаксис CLI проверен по исходникам argparse.
Нагрузочный инструмент и серверные ресурсы не проверены; масштаб не сертифицирован.
