# 0002. Источник расписания — открытый API РУЗ МГИМО

Дата: 2026-11-05. Статус: принято, импорт реализован — см. раздел «Реализация» ниже.

## Контекст

Решение 0001 предполагает импорт открытого расписания МГИМО, но источник и формат
оставались открытым вопросом.

## Что нашли

Страница <https://mgimo.ru/study/schedule/> ведёт на **РУЗ** — <https://ruz.mgimo.ru/ruz/main>
(«Расписание учебных занятий», типовая система Галактики, v1.16.23, как у ВШЭ).
Фронтенд — SPA на Angular, данные берёт из JSON-API на том же хосте (`apiUrl: /api/`).
На странице указано: опубликовано расписание осеннего семестра 2026/27, корректируется ежедневно.

Проверено 2026-11-05, авторизация и cookies не нужны, `curl` получает `200 application/json`:

| Эндпоинт | Что отдаёт |
|----------|-----------|
| `GET /api/dictionary/faculties` | список факультетов (`facultyOid`, `abbr`, `name`) |
| `GET /api/search?term=<строка>&type=group` | поиск групп: `id`, `label` (`1МО-01`), `description` = oid факультета. Слишком короткий `term` (2 символа) → `{"error":1}`, `1МО` уже работает |
| `GET /api/search?term=<строка>&type=person` | поиск преподавателей |
| `GET /api/schedule/group/<id>?start=YYYY.MM.DD&finish=YYYY.MM.DD&lng=1` | занятия группы за период |

Пример: группа `1МО-01` (`id=7814`), неделя 02–08.11.2026 — 39 занятий.
Полезные поля занятия: `date`, `dayOfWeek`, `beginLesson`, `endLesson`, `lessonNumberStart`,
`discipline`, `kindOfWork` (Лекция / Семинар …), `auditorium`, `building`, `stream`,
`subGroup`, `note`, `replaces`, `modifieddate`, `lessonOid`.

`robots.txt` на ruz.mgimo.ru нет (404).

## Решение

- Импорт расписания — из `ruz.mgimo.ru/api/schedule/group/<id>`, а не парсинг HTML.
- ~~Берём ограниченный набор групп.~~ Пересмотрено на интервью 2026-11-05: **берём весь вуз**,
  последовательно, с паузой 1 с между запросами.
- Поле `modifieddate` + `lessonOid` используем для диффа «перенос / замена»
  (диффер из Ikanam-schedule).

## Жёсткие ограничения (из CLAUDE.md)

- В ответе есть **реальные персональные данные преподавателей**: `lecturer`, `lecturerEmail`,
  `listOfLecturers`, `lecturer_rank`, `lecturer_title`, а также `author`. На импорте эти поля
  **не сохраняются**: преподаватель заменяется вымышленным ФИО, детерминированно по `lecturerOid`
  (один и тот же реальный преподаватель → один и тот же вымышленный). Сырые ответы API
  в репозиторий не коммитятся.
- Номера групп и названия дисциплин — не персональные данные, их оставляем.

## Риски

- API недокументирован и может измениться или закрыться → храним последний успешный снимок в БД,
  кабинет работает из БД, а не из живого API; дата снимка показывается.
- Сервер может ограничить частоту запросов → кэш + ночной импорт.

## Реализация (2026-11-05)

Решения с интервью: данные сразу в PostgreSQL (заложен каркас `app/`, SQLAlchemy, Alembic);
весь вуз; весь семестр, медленно; журнал изменений — уже в этом импорте.

Ещё два эндпоинта, найденные при реализации:

| Эндпоинт | Что отдаёт |
|----------|-----------|
| `GET /api/dictionary/groups` | все группы вуза одним ответом: 1534 группы, ~2 МБ, поля `groupOid`, `name` (`26МО-01`), `number` (`1МО-01`), `facultyOid`, `course`, `is_schedule` |
| `GET /api/dictionary/lecturers` | все преподаватели (3424) с **реальными** `fio`, `email` — используется только как стоп-лист фамилий, в БД не пишется |

Объём: семестр одной группы — ~800 занятий, ~3 МБ, ~3 с. Весь вуз за семестр — ~1534 запроса,
при 1 потоке оценка была **~70 минут**, при 2 потоках факт — **40 минут** (см. «Полный прогон»). Два режима:

- `python -m app.schedule.import_ruz --full` — весь семестр (первичная загрузка);
- `python -m app.schedule.import_ruz` — окно −7…+35 дней (ежедневный запуск, ловит изменения).

Устройство — `app/schedule/`:

- `ruz_client.py` — HTTP-клиент: пауза между запросами, повтор при 5xx/429/обрыве.
- `normalize.py` — **белый список полей**. Из занятия берутся время, дисциплина, вид, аудитория,
  корпус, поток, подгруппа и только oid преподавателя. ФИО, email, звание, `author`,
  а также свободный текст (`note`, `replaces`, `detailInfo`), где может оказаться ФИО,
  отбрасываются.
- `fake_names.py` — вымышленное ФИО из `sha256(соль:oid)`; одинаковое при повторном импорте.
  Вымышленные фамилии, совпадающие с реальной фамилией любого преподавателя РУЗ (в любом роде),
  исключаются; уже выданные имена с такими фамилиями переименовываются при следующем импорте.
- `importer.py` — загрузка и журнал `lesson_changes`: `added`, `changed`, `moved`, `cancelled`,
  `restored`. Правила — в docstring модуля, главные:
  исчезнувшее занятие помечается `cancelled`, а не удаляется; отмена фиксируется, только если
  все группы занятия загрузились; пустой ответ по группе с занятиями в БД считается сбоем;
  отмена + новое занятие той же дисциплины, вида и групп в пределах 14 дней — перенос;
  первичная загрузка журнал не заполняет.

Таблицы: `faculties`, `study_groups`, `teachers` (только oid и вымышленное ФИО), `lessons`,
`lesson_groups`, `lesson_teachers`, `lesson_changes`, `import_runs`.

Проверено на живом РУЗ 2026-11-05 (локальная SQLite, PostgreSQL на машине не было): 5 групп
1-го курса за семестр — 3233 занятия, 27 с. Два повторных импорта — журнал пуст, как и должно быть.
Аудит БД по справочнику 3424 преподавателей: 0 совпадений полных ФИО, сокращённых ФИО, email,
0 вымышленных фамилий, совпадающих с реальными.

**Не проверено:** работа на PostgreSQL — проверим при выкате на VPS. Полный прогон — см. ниже.

## Нагрузка на РУЗ: замер (2026-11-05)

Пауза в 1 с между запросами на деле почти ничего не стоила: она отсчитывается от начала
предыдущего запроса, а ответ за семестр РУЗ готовит 2–3 с. Узкое место — время ответа сервера,
поэтому ускорить можно только параллельными запросами.

Замер: по 12 запросов «семестр одной группы» в 1, 2 и 4 потока (параллельно шёл фоновый импорт
ещё в 1 поток):

| Потоков | Время ответа, медиана | Пропускная способность | Ошибки |
|---------|----------------------|------------------------|--------|
| 1 | 2,4 с | 0,42 запр/с | нет |
| 2 | 1,7 с | 1,17 запр/с | нет |
| 4 | 2,4 с | 1,54 запр/с | нет |

Ответов 429 нет: явного лимита по частоте не видно, упираемся в мощность сервера. На 4 потоках
время ответа уже растёт, прирост скорости небольшой. **Решение: 2 потока** (`RUZ_CONCURRENCY=2`),
минимальная пауза между началами запросов 0,5 с. Запись в БД остаётся последовательной.
Выше 4 потоков не проверяли сознательно.
