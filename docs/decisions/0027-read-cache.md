# 0027. Кэш чтений: расписание, лента колокольчика, повторные ответы ассистента

Дата: 21 ноября 2026. Статус: принято, реализовано (задача #24).
Постановщик: Legpopov (капитан), исполнитель raxlin4ik. Код и документ писал ИИ-агент,
ревью — капитан.

## Контекст

Каждая страница кабинета студента читает одно и то же. Главная дважды строит неделю
календаря (мобильный список дня и сетка для десктопа) и ищет ближайший экзамен; на каждой
странице колокольчик заново собирает ленту из четырёх журналов. Замер ниже: 18 SQL-запросов
на главную, 13 из них — к таблицам расписания. Ассистент на повтор того же вопроса заново
делает 3 вызова GigaChat, тратя лимит провайдера и минуту ожидания.

Импорт расписания выполняет **процесс бота** (раз в `BOT_IMPORT_HOURS`) и CLI
`python -m app.schedule.import_ruz`, а страницы отдаёт **процесс web**. Это разные процессы,
поэтому кэш, который импорт должен инвалидировать, обязан быть общим.

## Решение

### Хранилище: Redis, а без него — словарь в памяти

| Вопрос | Решение |
|--------|---------|
| Общий кэш | **Redis 7** (`redis.asyncio`), адрес в `CACHE_URL`. В `docker-compose.yml` — сервис `redis` (имя в сети `lms-redis`) без опубликованных портов, `maxmemory 64mb`, `allkeys-lru`, без записи на диск, `mem_limit 96m` |
| Без `CACHE_URL` | TTL-словарь в памяти процесса с LRU-вытеснением сверх 5000 записей: тесты, локальный запуск. Ограничение: импорт в другом процессе его не сбрасывает — свежесть только по TTL |
| Модуль | `app/cache/core.py` — один интерфейс `Cache` и два бэкенда; `app/cache/invalidation.py` — когда сбрасывать |
| Почему не только in-process | Импорт в боте не может сбросить словарь в памяти web. Почему не PostgreSQL-таблица: она снова ходит в ту же БД, а цель — разгрузить её |
| Сериализация | **JSON**, не pickle: из кэша нельзя «распаковать» исполняемый объект, а значения читаемы при отладке (`redis-cli get`) |
| Что лежит в кэше | Готовые к шаблону данные (dataclass → dict), **не HTML и не ORM-объекты**. HTML зависит от языка интерфейса, CSRF-токена и текущей даты; ORM-объект нельзя безопасно восстановить вне сессии. Шаблон рендерится каждый раз, это дёшево |

### Что кэшируется и ключи

Все ключи с префиксом `lms:v1:`. Смена формата значений — новый префикс, старые записи
уйдут по TTL.

| Данные | Ключ | TTL | Где |
|--------|------|-----|-----|
| Неделя календаря студента (пары группы с элективами по выбору студента + активности с отметкой записи) | `cal:s{student_id}:g{group_id}:{start}:{end}:{gen schedule}:{gen calendar:s{id}}` | `CACHE_SCHEDULE_TTL`, 30 мин | `app/web/calendar_view.py::week_for` — главная, `/schedule`, `/partials/day`, `/partials/calendar` |
| Ближайший экзамен группы на главной | `exam:s{student_id}:g{group_id}:{today}:{gen schedule}` | тот же | `app/grades/service.py::_next_exam` |
| Лента колокольчика (30 последних, с отметкой «прочитано») | `feed:u{user_id}:s{student_id\|0}:{gen notifications}:{gen notifications:u{id}}` | `CACHE_FEED_TTL`, 60 с | `app/notifications/service.py::feed` (бейдж, панель, страница) |
| Ответ ассистента | `asst:u{user_id}:{роль}:{язык}:s{выбранный студент\|0}:{as_of}:{сегодня}:{версия корпуса}:{sha256 вопроса}` | `CACHE_ASSISTANT_TTL`, 1 ч | `app/assistant/service.py::chat` |

**Студенты не смешиваются.** `student_id` и `user_id` берутся только из сессии (как и раньше
для запросов к БД), группа — из записи этого студента. Даже неделя группы, одинаковая для
одногруппников, хранится по ключу студента: в ней его элективы и его записи на активности,
а лишняя копия на 30 пар — килобайты. Тесты: два студента получают разные ключи и каждый
видит только своё; лента одного не содержит адресного объявления другого; ответ ассистента
одного пользователя не отдаётся другому.

### Инвалидация: поколения

Ключ данных содержит текущий **токен поколения**. Запись меняет токен (`bump`) — старые
ключи больше никто не читает, они уходят по TTL или LRU. Удалять ключи по шаблону не нужно.

- Токен — случайная строка, а не счётчик: если Redis вытеснит ключ поколения
  (allkeys-lru), появится новый токен, а не «0», с которым совпали бы старые записи.
- Поколения меняются **после** COMMIT. Гонка «читатель взял старый токен, прочитал БД
  до коммита, записал в кэш после сброса» безопасна: такая запись лежит под старым токеном.

| Поколение | Что его сбрасывает |
|-----------|--------------------|
| `schedule` | любая запись в `lessons`, `lesson_groups`, `lesson_teachers`, `teachers`, `study_groups`, `activities`: импорт РУЗ (после коммита каждой группы и явно в конце `ScheduleImporter.run`), `app.bot.demo_change`, seed |
| `calendar:s{id}` | `elective_choices`, `activity_signups` этого студента (сохранение элективов, запись на активность) |
| `notifications` | `announcements`, `certificate_request_events`, `grade_events`, `document_notices`, `document_recipients`, `courses`, `disciplines`, `students`: объявления деканата и преподавателя, статусы справок из Pyrus и вебхука, баллы и ДЗ, подтверждённые уведомления о документах |
| `notifications:u{id}` | `notification_reads` этого пользователя: «прочитано» и «прочитать всё» |

Мест записи много, и новые будут появляться, поэтому поколения сбрасываются не вызовами
в каждом сервисе, а **слушателями сессии SQLAlchemy** (`app/cache/invalidation.py`): `after_flush`
и `do_orm_execute` запоминают таблицы, `after_commit` внешней транзакции меняет поколения.
Слушатели подключаются в `app/db/session.py`, то есть в каждом процессе — web, бот, CLI.
Коммит точки сохранения (`begin_nested`) не считается: проверено опытом, что `after_commit`
вызывается и для него, поэтому стоит проверка `in_nested_transaction()`.

Ответы ассистента инвалидируются **версией корпуса** в ключе (mtime и размер `chunks.jsonl`):
публикация документа сотрудником переписывает файл, и старые ответы перестают совпадать.
Дата «сегодня» в ключе — потому что применимость редакций зависит от даты.

### Ассистент: что можно кэшировать

Кэшируется только **первый вопрос беседы** с итогом `answer` или `partial` **по публичным
положениям**. Не кэшируются: продолжения беседы (ответ зависит от истории), `not_found`,
`clarify`, ошибки провайдера, `unavailable`, запрос согласия на оценки, «лимит» (429 до
вызова сервиса), любые ответы с записями кабинета (`facts`, `personal_checked_at`, оценки) —
они меняются чаще часа, а оценки требуют согласия в конкретной беседе. Вопрос нормализуется
(регистр, «ё», пробелы, конечная пунктуация) после той же маскировки e-mail, телефонов и ФИО,
что и для истории; в ключ идёт sha256, текста вопроса в ключе нет. Попадание в кэш не тратит
поминутный лимит пользователя и записывается в историю беседы, как обычный ответ.

### Fail-open

Любая ошибка бэкенда (нет соединения, таймаут 0,5 с, битый JSON) логируется классом
исключения (не текстом: в нём бывает адрес с паролем), и запрос идёт в БД. После ошибки
Redis 5 с не опрашивается, чтобы недоступный сервер не добавлял таймаут к каждой странице.
`depends_on` web и бота на redis — `service_started`, не `service_healthy`: без Redis кабинет
должен стартовать. Тесты: поддельный бэкенд с исключениями и настоящий клиент на закрытом порту.

`python -m scripts.measure_cache -n 100` — временная sqlite, одна группа, 150 занятий
(30 в неделю), 8 активностей, 20 объявлений; запросы в приложение внутри процесса.
«Без кэша» — тот же код с бэкендом, который ничего не хранит. 21 ноября 2026, macOS, Python 3.14:

| Страница | Режим | SQL на запрос | из них расписание | среднее, мс |
|---|---|---|---|---|
| `/schedule` | без кэша | 8 | 6 | 5,5 |
| `/schedule` | с кэшем | 2 | 0 | 3,8 |
| `/` (главная) | без кэша | 18 | 13 | 7,6 |
| `/` (главная) | с кэшем | 5 | 0 | 4,3 |
| `/notifications/badge` | без кэша | 7 | 0 | 2,3 |
| `/notifications/badge` | с кэшем | 2 | 0 | 0,9 |

Оставшиеся 2 запроса — проверка сессии и пользователя; на главной ещё 3 — зачётка
(не кэшируется). Время на sqlite в том же процессе занижает выигрыш: на PostgreSQL по сети
каждый запрос — отдельный round-trip. Redis в этом замере не участвовал (локально его нет);
проверка `RedisBackend` выполнена на fakeredis (см. запись в `docs/prompts/cache.md`).

## Риски и ограничения

- **Без `CACHE_URL`** при раздельных web и боте импорт не сбрасывает кэш web: расписание
  обновится максимум через `CACHE_SCHEDULE_TTL`. На стенде Redis обязателен (docs/deploy.md).
- **Запись мимо сессии** (сырой `text()`, `engine.connect()`) поколения не сбросит. Сейчас таких
  записей в отслеживаемые таблицы нет; новый код такого рода должен звать `get_cache().bump(...)`.
- **Redis недоступен в момент записи** — сброс поколения теряется, данные останутся старыми до
  TTL. Поэтому TTL — страховка, а не украшение.
- **Лишние сбросы.** Импорт трогает `last_seen_at` всех занятий, поэтому сбрасывает кэш
  расписания у всех после каждой группы, даже без реальных изменений; сверка Pyrus с новым
  событием сбрасывает ленту у всех. Это лишние промахи, не устаревшие данные.
- **Содержимое Redis** — расписание студентов и заголовки их уведомлений (вымышленные данные).
  Redis без пароля, но виден только в docker-сети проекта. Для реальных данных нужен пароль в
  `CACHE_URL` (тогда это секрет `.env`) и TLS.
- **Объём.** Неделя календаря в JSON — порядка 10 КБ. На генераторе в 3000 студентов, открывших
  по две недели, это ~60 МБ — у предела `maxmemory 64mb`; тогда LRU вытесняет редко открываемое,
  а это просто промахи. Если на стенде будет видно много вытеснений (`redis-cli info stats`,
  `evicted_keys`), поднять `maxmemory` и `mem_limit`.
- Не кэшируются: расписание преподавателя, бот (`lessons_for`), `.ics`-подписка, зачётка.
