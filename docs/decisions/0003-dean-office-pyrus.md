# 0003. Взаимодействие с деканатом: справки через Pyrus

Дата: 2026-11-05. Статус: принято, серверная часть реализована (см. «Реализация»), экраны ЛК — после входа и сессий.
Источник: сократовское интервью с капитаном (Legpopov) о стороне деканата на примере справок.
Заменяет строку «Кабинет сотрудника» в [0001](0001-architecture.md).

## Контекст

Решение 0001 предполагало свой минимальный кабинет сотрудника с кнопками
«в работе / готово / отказ». Но в вузах деканат обычно уже работает в своих системах.
Если сотрудник ведёт заявки в Pyrus, в отдельный кабинет он заходить не станет. Поэтому
ЛК должен встраиваться в существующий процесс деканата, а не заменять его.

## Как устроено в вузе (модель, из которой исходим)

Модель взята из опыта капитана: он работает аналитиком в другом вузе. Для МГИМО это
**предположение**, см. «Допущения».

| Система | Роль |
|---------|------|
| **Pyrus** | Заявка на справку — это задача по форме. В ней идут шаги согласования, и здесь же хранится её статус (источник правды). Деканат открывает в Pyrus данные по конкретному студенту |
| **1С** | Контингент: факультет, курс, основа обучения, приказ о зачислении. Из этих данных формируется справка |

## Решения

| Вопрос | Решение |
|--------|---------|
| Сторона деканата | **Настоящий Pyrus**, тестовый аккаунт на бесплатном тарифе. Свой кабинет сотрудника **не делаем** |
| Доступ жюри | Заводим 1–2 тестовые почты, это универсальные сотрудники деканата. Жюри получает логин в ЛК (студент) и логин в Pyrus (деканат) |
| 1С | **Не подключаем.** Её роль играет наш PostgreSQL (seed из вымышленных студентов). В документе процесса и на схеме указано: в рабочей версии здесь была бы синхронизация с 1С |
| Создание заявки | ЛК создаёт задачу в Pyrus по форме «Справка» через API: вид справки, куда требуется, количество экземпляров, данные студента из нашей БД |
| Что видит студент | **Упрощённые статусы.** Все шаги согласования остаются в Pyrus. ФИО сотрудников в ЛК не показываются |
| «Нужна доп. информация» | Студент видит комментарий деканата и отвечает из ЛК **текстом и файлом**. Ответ уходит комментарием с вложением в задачу Pyrus, заявка возвращается в «На согласовании» |
| Синхронизация | **Вебхук от Pyrus** на наш URL на VPS, приходит мгновенно и запускает уведомление в Telegram. Плюс **фоновая сверка** открытых заявок раз в N минут на случай потерянного события |
| Pyrus не отвечает | Заявка сохраняется у нас со статусом «Принята», отправка в Pyrus повторяется в фоне. Студент ошибки не видит (выбор по умолчанию, капитан отдельно не подтверждал) |
| Готовый документ | **PDF формирует наш бэкенд по шаблону** из данных нашей БД, когда из Pyrus приходит событие о финальном шаге. В рабочей версии документ делала бы 1С |
| Электронная подпись | Имитация: **синий прямоугольник** на месте подписи. Настоящей ЭП нет, квалифицированную подпись не изображаем |
| Финал для студента | ~~Ссылка на PDF и сообщение «можно забрать оригинал»~~ **Уточнено по образцу ЛК РАНХиГС** ([разбор](../research/ranepa-lk.md), «Справки и выписки»): PDF доступен `CERT_DOWNLOAD_DAYS` дней (по умолчанию 30), бумажный оригинал — **по запросу и только после скачивания PDF**. См. «Бумажный оригинал» ниже |

### Статусы в ЛК

| Статус в ЛК | Когда |
|-------------|-------|
| Принята | Заявка создана в ЛК, задачи в Pyrus ещё нет (очередь отправки) |
| На согласовании | Задача в Pyrus создана и идёт по шагам |
| Нужна информация | Деканат запросил уточнение, студент видит комментарий |
| Готова | Последний шаг согласован, PDF сформирован, оригинал можно забрать |
| Отказ | Задача в Pyrus отклонена, студент видит причину |

### Бумажный оригинал (второй статус заявки)

Перенесено из ЛК РАНХиГС, одобрено капитаном («Да, перенеси»). У заявки два независимых статуса:

| Статус | Значения |
|--------|----------|
| Электронный | Принята → На согласовании ⇄ Нужна информация → Готова в электронной форме / Отказ; у готовой — срок скачивания, после него «Срок скачивания истёк» и PDF не отдаётся |
| Бумажный | нет → запрошен → готов к выдаче → выдан / не востребован |

- До первого скачивания PDF вместо кнопки — «Будет доступно после скачивания электронной справки».
- Запрос бумаги уходит в ту же задачу Pyrus комментарием «Студент запросил бумажный оригинал»
  (очередь, как у ответов студента). Закрытая задача при этом переоткрывается (`action: reopened`).
- Дальше ведёт деканат полем формы «Бумажный оригинал» (Готов к выдаче / Выдан / Не востребован).
  Через API мы это поле не пишем; пока оно пустое, в ЛК держится «запрошен».
- Вид «Справка о периоде обучения (для перевода)» — **только на бумаге**, как в РАНХиГС: PDF нет,
  оригинал запрошен сразу при создании (поле «Выдача» в задаче).

## Схема

```
Студент ──► ЛК (FastAPI) ──API: создать задачу──► Pyrus (деканат, шаги согласования)
              ▲   │                                      │
              │   └─ контингент из PostgreSQL            │ вебхук о событии
              │      (в рабочей версии — 1С)             ▼
              └──── статус / комментарий ◄──── /integrations/pyrus/webhook
                    PDF по шаблону                + фоновая сверка
                    уведомление в Telegram
```

## Безопасность

- Логин и ключ Pyrus, секрет подписи вебхука — только в `.env`.
- Входящий вебхук проверяется по подписи. Без валидной подписи запрос отклоняется.
  Задача из вебхука сопоставляется с заявкой по `pyrus_task_id` из нашей БД, а не по данным
  из тела запроса.
- Комментарии и файлы студента уходят только в задачу его собственной заявки (проверка
  владельца на уровне запроса к БД, как в 0001).
- В Pyrus попадают только вымышленные данные: это внешний SaaS.

## Допущения

| Допущение | Статус |
|-----------|--------|
| Деканат МГИМО работает по схеме «Pyrus — статус, 1С — данные» | **предположение**: перенесено из опыта капитана в другом вузе |
| API Pyrus позволяет читать задачи и шаги согласования | **проверено**: капитан автоматизировал выгрузку статусов согласования смет из Pyrus в Excel |
| На бесплатном тарифе Pyrus работают API и вебхуки | **со слов капитана**. Лимит пользователей на бесплатном тарифе не сверяли |
| Тестовый аккаунт Pyrus доступен до 28 ноября (конец жизни прототипа) | не проверено |

## Открытые вопросы

- ~~Как шаг Pyrus превращается в статус ЛК~~ — **решено: вариант А**, поле-список
  «Статус для студента». Запасной путь без поля: отклонение на шаге → «Отказ», закрытая
  задача → «Готова», иначе «На согласовании».
- ~~Как отличить комментарий для студента от внутренней переписки~~ — **решено**: студент
  видит только поле «Сообщение студенту», комментарии задачи ему не показываются.
- **Виды справок для МГИМО.** Пока три с одним шаблоном: об обучении, для военкомата,
  для посольства. Уточнить по открытым источникам.
- **Нужна ли теперь роль `staff` в нашем приложении.** Своего кабинета нет, но роль может
  пригодиться для админки или будущих интеграций.
- **Привязка бота к форме.** Документация Pyrus говорит только «добавьте бота в маршрут
  формы на нужном шаге». Будет ли вебхук приходить на каждое изменение задачи или только
  когда она у бота, проверим на тестовом аккаунте. Сверка раз в 5 минут закрывает оба случая.

## Реализация (2026-11-05)

| Файл | Что делает |
|------|-----------|
| `app/models/certificates.py` | `students` (контингент, роль 1С), `certificate_requests`, таймлайн `certificate_request_events` (он же очередь уведомлений: `notified_at`), ответы студента `student_replies` + `reply_files` |
| `migrations/versions/0002_certificate_requests.py` | Миграция |
| `app/certificates/pyrus_client.py` | Клиент Pyrus API v4: авторизация с кэшем токена и переавторизацией на `expired_token`/401, задачи, комментарии, загрузка файлов; проверка подписи вебхука |
| `app/certificates/status.py` | Задача Pyrus → статус ЛК и сообщение студенту |
| `app/certificates/service.py` | Сторона студента (создать, список, карточка, таймлайн, ответ, скачать PDF, запросить бумагу, подписи статусов для экрана — всё с фильтром по `student_id` в запросе) и `CertificateSync`: очередь отправки, отправка ответов и запросов бумаги, перечитывание открытых задач |
| `migrations/versions/0003_certificate_paper_status.py` | Срок скачивания и бумажный статус |
| `app/certificates/pdf.py` | PDF справки (reportlab). Скриншот: `docs/process/screenshots/2026-11-05-certificate-pdf.png` |
| `app/certificates/webhook.py`, `app/main.py` | `POST /integrations/pyrus/webhook`, `GET /healthz`, фоновая сверка раз в `PYRUS_SYNC_INTERVAL` |
| `app/certificates/sync.py` | Ручная сверка: `python -m app.certificates.sync [--loop]` |
| `tests/fake_pyrus.py`, `tests/test_certificates.py` | Поддельный Pyrus и 16 тестов сценария |

Детали поведения:

- После ответа студента статус в ЛК сразу «На согласовании». Сохраняется, на какое
  сообщение деканата он ответил: пока поле «Сообщение студенту» не изменилось, «Нужна
  информация» в ЛК не возвращается, даже если сотрудник ещё не переключил список.
- Файлы ответа: до 5 штук, до 10 МБ каждый, хранятся в БД. Если файл загрузился в Pyrus,
  а комментарий упал, при повторе файл заново не грузится (guid сохранён).
- На «Готова» PDF формируется один раз и кладётся в БД. Затем он прикладывается к задаче
  Pyrus комментарием (чтобы деканат распечатал оригинал); если это не удалось — повторится
  при следующей сверке, студенту PDF доступен сразу.
- Заявки в статусах «Готова» и «Отказ» больше не перечитываются, если бумага не в работе
  (запрошена или готова к выдаче). Электронный статус после «Готова»/«Отказ» не меняется,
  даже если задачу переоткрыли ради бумаги.
- Первое скачивание PDF запоминается (`downloaded_at`) — оно открывает запрос бумаги.
  Срок скачивания (`download_until`) фиксируется в момент готовности.
- Вебхук отвечает сразу пустым 200, задачу перечитывает в фоне через API. Тело вебхука
  используется только ради `task_id`, а заявка ищется по `pyrus_task_id` в нашей БД.

## Настройка Pyrus (один раз)

1. **Форма «Справка»** со следующими полями (имена — точно такие, по ним пишет ЛК):

   | Поле | Тип | Кто заполняет |
   |------|-----|---------------|
   | Студент | текст | ЛК |
   | Номер зачётки | текст | ЛК |
   | Факультет | текст | ЛК |
   | Курс | число | ЛК |
   | Форма обучения | текст | ЛК |
   | Основа обучения | текст | ЛК |
   | Вид справки | текст | ЛК |
   | Куда требуется | текст | ЛК |
   | Количество экземпляров | число | ЛК |
   | Номер заявки ЛК | текст | ЛК |
   | Статус для студента | список: На согласовании, Нужна информация, Готова, Отказ | сотрудник |
   | Сообщение студенту | многострочный текст | сотрудник |
   | Выдача | текст | ЛК («электронно, оригинал по запросу» / «только на бумаге») |
   | Бумажный оригинал | список: Готов к выдаче, Выдан, Не востребован | сотрудник |

   Маршрут — по вкусу (например, «проверка в деканате» → «подпись декана»). Шаги в ЛК
   не видны.
2. **Бот** (раздел Боты → «Добавить бота»): URL `https://<домен>/integrations/pyrus/webhook`.
   Его Login и Security Key — в `.env` как `PYRUS_LOGIN` / `PYRUS_SECURITY_KEY`. Добавить
   бота в маршрут формы (наблюдателем или на первом шаге) и дать ему право создавать
   задачи по форме.
3. `PYRUS_FORM_ID` — id формы. После запуска: заказать справку тестовым студентом,
   в Pyrus выставить «Нужна информация» + сообщение, ответить из ЛК, закрыть задачу —
   в ЛК появится PDF. Скачать его, запросить оригинал — задача переоткроется с комментарием;
   выставить «Бумажный оригинал: Готов к выдаче», затем «Выдан».
4. Для жюри — 1–2 тестовые почты сотрудников деканата в Pyrus, логины в `docs/test-accounts.md`.
